# ピクト君 散剤監査 v0.2.0

薬局での散剤調剤を補助する、端末内処理のWebアプリです。処方、瓶のGS1、電子天秤の重量を突合します。薬剤師の最終監査を代替しません。

## 今回の範囲

指示書に沿って、基本監査を検証した後に処方取り込みを独立モジュールとして追加した開発版です。

実装済み：ピクト君UI、テスト処方、外部マスターCSV/JSON取込、GS1読取、コード・成分・規格・剤形照合、天秤OCR、確認登録、重量累積、±10%判定、3種類の音、薬剤違いの監査停止、訂正・削除を含む履歴、端末保存、PWA、GitHub Pages用ビルド。

追加実装：処方箋QR/JAHISの共通薬剤レコード解析・分割QR結合、電子処方箋控えのJAHIS情報、日本語の紙処方箋OCR（四隅指定・台形補正・回転・コントラスト補正）、実薬マスターからの処方手入力、共通形式JSON、一般名コードと成分・規格・剤形が完全一致する商品の照合。

専用7セグメント認識、電子処方箋管理サービスとの通信、国内全薬剤を網羅したマスターは含みません。未解釈データから推測して監査を開始する機能はありません。医療機関・レセコンごとの実際のQR、手書き処方、各種天秤、iPhone/Android実機での検証は未完了です。

実薬マスターや実機画像は同梱していません。今回の動作検証は架空TESTデータと合成画像によるものです。

## 起動

Node.js 24、pnpm 11を使用します。

```sh
pnpm install --frozen-lockfile
pnpm dev
```

表示されたlocalhostのURLをブラウザで開いてください。`index.html`のダブルクリック（file://）では動作しません。

```sh
pnpm test
node scripts/barcode-check.mjs
pnpm build
pnpm preview
```

初回のビルド・開発起動時だけ、公開配布元から日本語・英語OCR学習データを取得します。OCRエンジン、学習データ、GS1デコーダは `public/vendor/` にコピーされ、公開後の処理に外部CDNは使いません。

## まず試す

1. 「テスト処方で試す」を押します。
2. テスト散剤A、1日量2.00g、10日、総量20.00gを確認して「この内容で監査開始」。
3. 「GS1を読む」で `TEST000001` を入力して照合します。
4. 「重量を手入力」で `7.00` → 数値確認 → チェック → 登録。
5. 再び `TEST000001` を照合し、`13.02` を確認・登録。
6. 合計20.02g、差+0.10%、合格を確認します。

`TEST000002` は別成分、`TEST000003` は同一成分の規格違いです。赤い全画面警告と監査停止を確認できます。警告画面で確認しない限り進めず、再読み込みでも停止は残ります。確認後も必ずGS1から再開します。

`public/data/TEST000001.png` はTEST文字列を収めたQR画像です。写真読取・印刷してカメラ読取の導線を検証できます。これは実薬GS1ではありません。実在GTINを架空薬へ割り当てていません。

## 処方情報

処方QR、紙処方箋OCR、共通形式JSON、マスターからの手入力、テスト処方に対応します。いずれも原本との人による確認後に開始します。

### 処方箋QR / 電子処方箋控え

「処方を取り込む」→「処方箋・控えのQR」。カメラ、画像、JAHISテキストファイルを利用できます。JAHISは既定でShift-JISを使用し、UTF-8も選べます。分割QRは連番・組番号で集め、欠落・矛盾した重複がある間は解析しません。

[JAHIS院外処方箋2次元シンボル記録条件規約Ver.1.11](https://www.jahis.jp/standard/detail/id=1233)を参照しています。JAHIS2～11のヘッダーを受け付け、101/102/111/201の共通部分からRp、コード体系、薬剤名、数量、数量基準、用法、日数・回数を取り出します。規約全項目に準拠する実装ではありません。

分割処方、頓服、力価、補足用法、単位変換などがある場合は、単純な日量として計算せず、人による製剤総量の確定を求めます。レセプト電算・YJ・一般名コードはマスターの候補を絞るために使い、薬剤の選択・確認は人が行います。コードなし・HOT等の未対応コード体系は名前で合格にせず、原本を見てマスターを選択します。コード付き処方と異なる薬剤を選んだ場合は拒否します。

電子処方箋控えもJAHISの薬剤情報が含まれる場合に同じ確認へ進みます。引換番号やURLだけの場合は薬剤情報を得られないため処理を停止し、写真／手入力を案内します。患者情報を外部サービスへ問い合わせる実装はありません。

### 紙処方箋OCR

「紙処方箋OCR」で撮影または画像選択後、処方欄の四隅を左上から時計回りに指定します。射影変換で台形を補正し、必要なら角度を指定して回転します。コントラスト補正後の画像を確認し、日本語＋英語の専用OCRワーカーで認識します。四隅や傾きの自動推測はしません。

認識結果は必ず表示します。患者情報を除いた薬剤部分だけを残し、1剤ごとに空行で区切って確認してください。薬剤名の誤字を自動訂正しません。数量は明示された数値・単位・日数を候補として取り出し、1日量／1回量／全量が不明なら選択が必要です。数字の全半角等は数値候補の解析時に正規化しますが、OCR原文は変えません。

各薬剤のマスター選択、成分・規格・剤形、製剤総量gを確認し、全薬剤の読み取り漏れがないことを確認した後、さらに最終確認画面の「この内容で監査開始」で確定します。錠剤等を対象外にする際は理由を記録します。元画像・OCR全文・患者情報レコードは永続保存しません。

JSONは薬剤配列、または `{ "drugs": [...] }` を受け付けます。形式は `public/data/demo-prescription.json` を参照し、実薬では有効な医薬品コードを指定してください。氏名・生年月日・元QRなど、定義外の項目は保存しません。薬剤名・用法・自由記述欄に患者個人情報を入れないでください。

主要項目：

| 項目                                       | 内容                                |
| ------------------------------------------ | ----------------------------------- |
| prescriptionType                           | `brand` / `generic` を明示          |
| drugCode / receiptCode                     | 商品名処方のYJ / レセプト電算コード |
| genericCode                                | 一般名処方の一般名コード            |
| drugName, ingredient, strength, dosageForm | 薬剤名、成分、規格、剤形            |
| expectedTotal                              | 確認した製剤総量                    |
| unit                                       | 本版の重量監査は明示した `g` のみ   |
| quantityBasis                              | `product`（製剤量）を明示           |
| rpNumber, sourceType                       | Rp番号、入力経路                    |
| quantityPerDay, days, usage                | 任意の明示情報                      |

手入力は数量の意味を選ぶまで総量を算出しません。1日量×日数、1回量×1日回数×日数、または明示した全量から計算します。mg、成分量、頓服で回数不明などは自動換算しません。原本を確認し、製剤の全量gを入力してください。JSONの `expectedTotal` は入力者が確定した全量であり、日数等から勝手に置き換えません。

散剤、細粒、顆粒、ドライシロップを監査対象とします。ドライシロップは調製前の粉末製剤量であることを人が確認してください。QR/OCRでは錠剤等を明示的に対象外として処理できます。共通JSONはgでの監査用データを受け付ける形式で、錠数など異なる単位は直接重量として受け付けません。

## GS1と医薬品マスター

ZXing-WASM 2.2.1のDataBar、DataBar Limited、DataBar Expanded、Code128、DataMatrixを使用。QRはTESTコード検証等に使えます。読み取り後、GS1のAI(01)または14桁GTINを取得し、チェックデジットを検証します。GS1 Digital Link URLや13桁JANの暗黙補完は行いません。

SafariでBarcodeDetector APIがなくてもWASMデコーダを使用します。カメラの読取成功後は停止し、許可トークン1個につき重量を1回だけ登録できます。手入力GTIN・外部スキャナー入力も同じ照合を通ります。複数コードを検出した写真は選択を推測せず読み直します。

商品名処方はYJまたはレセプト電算コードが一致し、双方に存在するコードの矛盾がなく、成分・規格・剤形も一致することが必要です。名前だけでは合格しません。

一般名処方は一般名コード・成分・規格・剤形がすべて一致した場合に適合とします。同じ一般名コードに対して成分・規格・剤形が矛盾するマスターは拒否します。表記揺れや含量の同値変換、後発品への曖昧な置換は行いません。正規化・対応付けは確認済みマスター側で管理してください。国内全医薬品の対応を保証するものではありません。

### マスター更新

監査開始前に「医薬品マスター」からCSVまたはJSONを選び、検証結果を確認して更新します。検証失敗時は既存マスターを変更しません。監査中のマスター変更はできません。監査記録には秤量時の商品情報の写しが残ります。

CSVひな形：`public/data/master-template.csv`。UTF-8、見出しは下記英字です。コードは文字列として扱い、表計算ソフトで先頭ゼロを消さないでください。

```text
gtin,yjCode,receiptCode,genericCode,productName,genericName,ingredient,strength,dosageForm,manufacturer,salesStatus
```

必須はGTIN、YJまたはレセプト電算コード、商品名、成分、規格、剤形。GTIN重複は拒否します。一般名監査には一般名コードと対応情報も必要です。販売状態は保存・参照情報であり、販売中止・回収等の自動判定データベースは持ちません。

## 天秤OCR

カメラでは表示枠内だけを切り取り、画像選択ではスライダーでROIを指定します。元画像とコントラスト補正画像の2通りをTesseract.jsで認識します。数字・小数点・符号と単位候補を読み取り、`mg`や`kg`を`g`と誤解しないようにします。

結果が一致しない場合や信頼度85%未満は低信頼度として表示します。片方のみが「数値+g」を得た場合、その値を低信頼度候補として提示します。両方の有効数値が異なる場合は自動選択しません。小数点・単位を推測して修正せず、すべての結果で目視確認と登録操作が必要です。元画像やOCR全文は永続保存しません。

7セグメント、反射、暗さ、低コントラスト、カンマ、符号、単位が枠外などでは読めないことがあります。信頼度はエンジンの指標であり、正答率を示しません。撮り直し／手入力で確認します。`702g`のように認識した値が処方量を超える場合は警告を表示し、誤認値を勝手に`7.02g`へ変更しません。

## 累積と判定

- 未登録：未秤量
- 90%未満：秤量継続
- 90%以上110%以下：合格（境界を含む）
- 110%超：重量超過

重さは小数6桁のgまで受け付け、整数化して累積・境界を比較します。画面は最低2桁、必要なら6桁まで表示し、丸めで登録値を隠しません。薬剤・処方・秤量回数に固定の件数上限は設けていません。保存容量はブラウザの上限に依存します。

全対象が合格するまで監査完了にせず、訂正・削除時にも再計算します。誤登録を削除しても記録は残り、そのGS1許可を使い回せません。訂正には理由と確認が必要です。

## 保存・履歴

localStorageに薬剤、処方、秤量、判定、警告、訂正履歴を保存します。患者画像・原本画像は保存しません。クラウドへの自動送信、アクセス解析、外部フォントはありません。別タブの更新はrevisionとWeb Locksで競合を検出します。保存失敗時は登録済みにしません。再読込では重量登録許可を復元せず、GS1から再開します。

完了後の「この処方のデータを終了」は確認を経て端末履歴へ移動します。JSONを書き出してバックアップできます。ブラウザのデータ削除、別端末、別オリジンへの移動では共有・復元されません。履歴は改ざん防止署名付きの法定監査記録ではありません。

## 通知・ブラウザ

正常音、重量超過音、薬剤違いの強い警告音をWeb Audioで作成。対応ブラウザでは薬剤違いに長短を組み合わせた振動を追加します。音量の強制変更はしません。

対象設計はiPhone Safari、Android Chrome、Windows / Mac Chrome系です。カメラにはHTTPSまたはlocalhostが必要です。Safariの振動非対応などは画面と音で補完します。実機カメラ、消音・バックグラウンド時の音、Safari/Androidでの長時間運用は別途現物検証が必要です。

## PWA / GitHub Pages

ビルドでService Workerを生成し、OCR学習データを含めて同一オリジンへ配置します。初回はオンラインで開き、下部に「オフライン対応」が表示されるまで待ちます。OCR・GS1資材は約58MBあり、初回の準備には時間がかかります。更新は既存タブをすべて閉じてから再度開くと反映されます。

### 新しいGitHubリポジトリから公開

1. このフォルダーのソースを新しいリポジトリのmainへpushします。既存pill-counterへ上書きしないでください。
2. Settings → Pages → Build and deploymentで「GitHub Actions」を選択。
3. 同梱の `.github/workflows/pages.yml` を実行します。
4. 成功したPagesのHTTPS URLをスマートフォンで開きます。

Viteのbaseは相対パスなので、`/powder-audit/`などのサブパスにも配置できます。ビルド済みファイルは `dist/`。ソース、テスト、患者データを公開ディレクトリへ混在させず、公開するのはdistの静的資材だけにします。

この納品時点ではGitHubへのpushと本番公開は行っていません。

## 構成・検証

`src/domain.ts` に照合と監査状態、`storage.ts` に保存、`camera.ts` に読取、`ocr.ts` に天秤OCR、`paper.ts` に処方箋補正・日本語OCR、`prescription.ts` にJAHIS・OCRテキスト解析、`prescription-ui.ts` に入力確認、`sound.ts` に通知、`main.ts` に主画面を分離しています。

`pnpm test` は指定の境界・薬剤違い・一般名・単位・確認・履歴・保存失敗を検証します。`scripts/barcode-check.mjs` は全ゼロの合成テストデータを使い、DataBar/Limited/Expanded、GS1-128、TEST QRの生成・読取を検証します。合成テストバーコードを実薬に貼付しないでください。
